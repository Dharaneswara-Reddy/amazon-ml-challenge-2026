# B — Blocking recall research (v3)

Goal: raise candidate-generation recall from 94.46% (v2, K=3) to >=98.5% at <= ~25 candidates per S1.
Scripts: notebooks/v3_research/. Findings appended incrementally below.

## Baseline facts (from artifacts/cache/learned/ranker.json)
- 5% sample of fit-group rights: uncapped union recall plateau = 95.19%; learned linear ranker K=3 keeps 95.00%, K=5 95.14%.
- => The top-K cut loses only ~0.2 pp. ~4.8 pp of true pairs are NEVER generated by any pass. Recall work = new passes.

## Q1. Missed pairs: never generated vs cut by top-K  (script b01_misses.py)
- Train GT pairs 7,638,365; missed by cand_train (K=3) 423,382 -> recall 94.457%.
- Miss rate by country: India 202,065 / 3,059,843 = 6.60%; US 221,317 / 4,578,522 = 4.83%. S2 204k / S3 219k misses (balanced).
- Misses whose right id is in union_sample (5% of fit rights): 21,109. Of those only **774 (3.7%) were generated by
  some pass but cut by the K=3 ranker; 20,335 (96.3%) were never generated by any pass.**
- => Better ranking/larger K can recover at most ~0.2 pp. The remaining ~5.3 pp needs new candidate passes.

| name token Jaccard mean / median | 0.52 / 0.50 | 0.81 / 1.00 |
| address token Jaccard mean / median | 0.39 / 0.43 | 0.80 / 0.88 |
| # shared name+addr tokens (median) | 5 | 8 |
| median left-df of the RAREST shared token | **444** | 25 |
| has >=1 shared token with left df <= 100 | **26%** | 75% |

**Root cause #1: df caps.** 74% of misses share no token whose left document frequency is <= 100 (the token pass cap).
Example: `Liberty Trust | 1940 Fisher Road, Unit 33D, Atlanta, GA` vs `Liberty Trust | 1940 FISHER RD, ATLANTA TOWNSHIP, GA`:
50 US S1 records are named "liberty trust", and "liberty", "trust", "1940", "fisher", "atlanta" each exceed df 100, so the
token pass emits nothing; the sorted-neighbourhood keys put "33d" (unit) before "atlanta" in the sorted address words so
the key is far from the right's key. But the *combination* `1940 + fisher` has left df 6 (one building). => the fix is
**compound keys** (token pairs), not wider single-token caps.
**Root cause #2: sorted-neighbourhood fragility** — a single inserted/removed leading word (unit "33d", "block e 609",
"dr", "shri", "m/s") moves the key far away in sort order; window 3 is tiny when 50 S1 share the name.

## Q3. Prototype passes (scripts b03_base.py, b05_passes.py, b06_phon.py, b07_union.py)

Setup: all 2,206,821 train S1 on the left; right = 5% hash subset of S2∪S3 (`hash(entity_id) % 20 = 0`, 516,869
records, 382,703 GT pairs, baseline v2 K=3 recall on it = 94.50%). Each prototype is a **compound-key IDF pass**: key set
per record (country-scoped, hashed to UBIGINT), keep keys with left df <= cap, score (lid,rid) by summed
ln(1+NL/dl) over shared keys, keep top-k lids per rid. Runtimes are on the subset (x~20 for full train rights, but key
tables for L are built once).

| na | name word x address word | 30 | 5 | 30.1 | 4.03 | 83.7% | **+1.91 pp** | 34.7% | 29 |
| nn | name word x address number | 50 | 5 | 15.7 | 2.88 | 68.8% | +1.60 pp | 29.0% | 6 |
| n2 | unordered name word pair | 30 | 5 | 7.6 | 2.19 | 53.0% | +0.61 pp | 11.1% | 5 |
| ph | single phonetic name word (voiced->unvoiced, no vowels) | 300 | 5 | 29.3 | 1.30 | 5.4% | +0.02 pp | 0.4% | 10 |
| ph2 | phonetic name word pair | 30 | 5 | 9.8 | 2.51 | 45.6% | +0.48 pp | 8.7% | 6 |

## Q3(g) + ranker: how to cut the expanded union (b10_rankfeat.py, b11_ranker.py)
Union = v2 K=3 candidates ∪ {px, hs, n2, na, phx, aa}: 7.93M pairs on 516,869 subset rights (15.3/right), ceiling
98.35% of GT on the held-out half (split by `hash(rid||'x') % 2`, train ranker on the other half).
Cheap features: per-pass scores (NULL if not generated), n_pass, JW(name_core), JW(space-stripped name), JW(phonetic
name), JW(sorted address words), address-token Jaccard, name-token Jaccard, #shared numbers, right address length,
right #numbers.

| cut rule (held-out half) | recall | pairs / right |
|---|---|---|
| legacy linear (jw_core+jw_addr+jacc_addr+0.3·num) top-1 / 2 / 3 / 5 / 10 | 95.97 / 97.26 / **97.86** / 98.21 / 98.32% | 1 / 2 / 3 / 4.95 / 9.5 |
| LightGBM (binary, 300 trees) top-1 / 3 / 5 per right | 95.6 / 97.8 / 98.1% | 1 / 3 / 4.95 |
| LightGBM p >= 0.001 (global threshold, no per-right K) | 97.8-98.0% | **1.55** |
| LightGBM p >= 0.0001 | 98.08% | 2.70 |
| **legacy top-1 OR LightGBM p >= 0.001** | **98.22%** | **1.64** |
| legacy top-2 OR p >= 0.001 | 98.27% | 2.40 |
| legacy top-3 OR p >= 0.001 | 98.30% | 3.26 |

Findings:
- The linear ranker is as good as LightGBM at *top-K per right*; a per-right K is wasteful because most rights have one
  obvious candidate. A **global probability threshold** from a small GBDT keeps the same recall with half the pairs.
  The hybrid "top-1 by linear score OR p >= 1e-3" reaches 98.2% at 1.64 pairs/right (~7.7 per S1 in train vs 14 today).
- LightGBM importance: jw_phn, r_addr_len, jw_core, jacc_addr, n_pass, jw_strip, jw_addr — the phonetic / stripped-name
  JWs matter (they reach the transliterated and concatenated names).
- Run-to-run noise of the threshold rule ~0.1-0.2 pp (LightGBM bagging on unordered DuckDB fetch); fix row order + seed.
- Re: "raising K for rights with a small top-score gap" — subsumed by the global threshold: a right with several
  near-tied candidates gets several above threshold automatically.

## Q3(f) S2<->S3 transitivity (b12_transitive.py)
Residual misses after v2 ∪ {px,hs,n2,na,phx,aa}: 6,248 (1.63% of subset GT). 5,930 of them have a sibling right (another
S2/S3 record of the same S1) that IS a v2 candidate; the sibling's name is identical for 2,178 and JW>=.92 for 3,492.
Actual pass "right r -> rights r' with the same (country, name_core) and right-df <= cap -> top-1 v2 left of r'":
cap 5: +0.031 pp over v2+new passes at 0.37 pairs/right; cap 20: **+0.093 pp at 1.03 pairs/right**. The sibling link
exists but names shared by the siblings are also shared by distractors, so it is weak. Low priority.

## Q4. Structural shortcuts (b13_structure.py)
- No leakage: Spearman(ID number S1, ID number of its match) = 0.001; Spearman(row position S1, row position match) = -0.003.
- Distractors: 26% of subset rights have no match. Their best v2 candidate has JW(name)>=.9 for 77% (vs 90% for matched
  rights) and name+address close (JW>=.9 & addr Jaccard>=.5) for 59% (vs 81%) -> distractors are near-copies of real
  S1 businesses. But the S1 "parent" of a distractor has true matches 91.5% of the time vs 94.4% base rate -> there is
  no exploitable "parent without matches" pattern. No shortcut for blocking.

## Q5. Recommendation, expected recall and cost

**Recommended pass set (added to the existing v2 passes):**
1. `px` — 6-char prefix of space-stripped name_core × each (address number | address word len>=3); left df cap 30; top-5.
2. `hs` — each of the 5 largest address numbers × each address word len>=3; left df cap 50; top-5.
3. `n2` — unordered pairs of name_core words (len>=2); left df cap 30; top-5.
4. `na` — name word × address word; left df cap 30; top-5.
5. `phx` — whole sorted phonetic-skeleton name, exact; left df cap 30; all (<=30).
(optional `aa` address word bigram/skip-gram cap 30: +0.08 pp for +2.5 pairs/right; transitivity +0.09 pp: skip.)

**Cut:** replace "top-K per right by linear score" with **keep the linear top-1 per right OR LightGBM p >= 1e-3**
(small binary GBDT on ~17 cheap features incl. JW of phonetic and space-stripped names; trained on fit-group rights).

**Expected (5% right subset, held-out half):** union ceiling 98.35%; after the cut **98.2% recall at 1.64 pairs per
right** (top-2 OR p>=1e-3: 98.27% at 2.40; top-3 OR: 98.30% at 3.26). Today: 94.5% at 3.0 pairs/right.
Per S1: train 4.67 rights/S1 -> ~7.7 (1.64/right) to ~11 (2.4/right) candidates per S1; test has ~5.7 rights/S1 ->
~9-14 per S1. Well inside the <=25 budget; the candidate file actually shrinks vs today (14 train / 17 test).
Realistic ceiling is ~98.5%: ~1 pp are right records with an empty address and a name shared by dozens of S1.

**Runtime (measured on 5% of rights, all 2.2M S1, 4 threads, 3 GB):** px 16 s, hs 21 s, n2 5 s, na 29 s, phx 3 s,
union+features 90 s for all six passes. Left key tables (px 14.5M, hs 18.7M, na 28M, n2 5.3M rows) are built once; the
join scales with rights: raw join pairs/right px 13.9, hs 32.8, na 30.1, n2 7.6. Full train (10.3M rights) estimate
~10-15 min for the five passes when run in 8 right-hash buckets (same as token_pass), plus ~15-20 min for union
features (~13 pairs/right x 10.3M = 135M pairs, jaro_winkler in DuckDB). Test similar (11.1M rights). Memory: hashed
UBIGINT keys + int ids keep it under 3 GB; DuckDB spill must go to disk, not /tmp (tmpfs = RAM on this laptop).

### Implementation sketch (DuckDB; reuse token_pass machinery)
```sql
-- key tables (T = L or R); NUMS = 5 largest distinct numbers of addr_nums; AW = distinct addr words len>=3, non-numeric
CREATE TABLE Tk_px AS SELECT DISTINCT id, hash(c || '|' || substr(replace(name_core,' ',''),1,6) || '#' || x) AS k
  FROM (SELECT id, c, name_core, list_concat(NUMS, AW) xs FROM T WHERE length(replace(name_core,' ','')) >= 6), unnest(xs) u(x);
CREATE TABLE Tk_hs AS SELECT DISTINCT id, hash(c || '|' || n || '#' || w) AS k FROM (SELECT id, c, unnest(NUMS) n, AW aw FROM T), unnest(aw) u(w);
CREATE TABLE Tk_n2 AS ... least(a,b) || '#' || greatest(a,b) over name words a<b;
CREATE TABLE Tk_na AS ... name word || '#' || addr word;
CREATE TABLE Tk_phx AS SELECT id, hash(c || '|' || phn) FROM T WHERE phn <> '';   -- phn precomputed in normalize
-- per pass
CREATE TABLE kdf AS SELECT k, ln(1 + NL::DOUBLE / count(*)) idf FROM Lk GROUP BY k HAVING count(*) <= cap;
-- per right-hash bucket b:
INSERT INTO cand_px SELECT lid, rid, s, b FROM (SELECT l.id lid, r.id rid, sum(idf) s
  FROM (SELECT * FROM Rk WHERE hash(id) % 8 = b) r JOIN kdf USING (k) JOIN Lk l USING (k) GROUP BY ALL)
  QUALIFY row_number() OVER (PARTITION BY rid ORDER BY s DESC, lid) <= 5;
```
- Right-side df cap is not needed (left cap bounds the join at cap × #keys per right).
- `phn` (phonetic skeleton) = per word: ph->f, sh->s, ch/kh/gh->k, th->t, bh->b, dh->d, jh->j, x->ks, [gqc]->k, b->p,
  d->t, [vw]->f, z->s, j->s; drop [aeiouhy] after the first char; collapse repeated letters; sort words. Do it in Python
  in normalize (cached per word: 2.2M names in 17 s) — DuckDB RE2 has no backreferences and Python UDFs are too slow.
- Union: add in_px/in_hs/... flags and s_* scores; add features jw(phn), jw(space-stripped name), name Jaccard,
  right address length, #shared numbers; then the hybrid cut. Train the GBDT cut on fit-group rights only.
- Char 4-gram pass on stripped names (`s4`, df cap 1000) blew up (>6 GB spill, raw volume ~15 grams × up to 1000
  lefts per right) — `px` covers the concatenated-domain case at a fraction of the cost. TF-IDF/MinHash on name+addr
  was not needed: compound keys are the sparse, exact version of the same idea and are cheaper in DuckDB.
