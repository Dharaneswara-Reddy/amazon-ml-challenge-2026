# Business entity resolution: winning competition solutions and SOTA pairwise matchers

## Kaggle "Foursquare - Location Matching" (2022) top solutions

### Takeaway
Top teams used a multi-stage funnel (geo/text blocking → LightGBM candidate reduction → richer LightGBM/GBDT feature model → optional transformer/GNN reranking → graph post-processing), evaluated by mean IoU. A strong solution (7th/1083) reached maxIoU 0.9935 on 32 candidates/sample using only LightGBM + embeddings + contrastive-learned features — **no transformer needed** to place highly — while 1st place added transformer rerankers and a GNN post-processing stage on top of GBDT. Kaggle's writeup/discussion pages are JS-rendered and could not be scraped directly (WebFetch returned only the page `<title>`), so exact 1st/2nd-place IoU and recall numbers were not independently confirmed beyond what search snippets surfaced.

### Cited Findings
- 1st place ("Team 2:30" / re:waiwai, DeNA Inc. + collaborators): 4-stage pipeline — (1) candidate generation via geographic proximity + TF-IDF text similarity, (2) a Transformer-based blocking stage to cut candidates while keeping recall high, (3) an ensemble of LightGBM + XGBoost + BERT-based language models for final match classification — [Kaggle 1st place writeup](https://www.kaggle.com/competitions/foursquare-location-matching/writeups/re-waiwai-1st-place-solution) (content confirmed via search snippet only; direct fetch blocked by JS rendering).
- A described 4-stage general framework used by top teams: candidate generation (text + geo) → LightGBM filtering → pairwise classification by two transformer language models → post-processing node classification via a Graph Neural Network (GNN) — [search-surfaced summary, original writeup](https://www.kaggle.com/c/foursquare-location-matching/discussion/336062).
- 2nd place (Team 2:30, colum2131 part, DeNA Inc.): stage 1 = candidates from text similarity + geographic proximity; stage 2 = a first LightGBM with a *limited* feature set to cheaply cut candidates (memory-efficient); stage 3 = top-40 candidates/id fed into a second, richer LightGBM using Levenshtein/Jaro-Winkler string distances, statistical ratios, Euclidean lat/long distance, and SVD-reduced name embeddings; stage 4 = added transformer BERT-based LMs, iteratively fine-tuned via CV/LB feedback — [Kaggle 2nd place writeup](https://www.kaggle.com/competitions/foursquare-location-matching/writeups/2-30-2nd-place-solution-colum2131-part) (via search snippet; direct fetch blocked).
- Competition metric: submissions scored by **mean IoU (Jaccard index)** between predicted and ground-truth match sets per location — [search-surfaced summary of competition overview](https://www.kaggle.com/c/foursquare-location-matching/discussion/335800).
- A detailed 7th-of-1083 place Japanese write-up (Future Architect) reports concrete numbers: **32 candidates generated per sample**; retrieval-stage recall expressed as **maxIoU = 0.9778** at the candidate stage; **final maxIoU = 0.9935** after post-processing; LightGBM tuned with **num_leaves = 4096** (found optimal at 2^12) and **2000 boosting iterations**, with prediction accelerated ~100x using ForestInference on GPU; embeddings trained via self-supervised contrastive learning gave name-embedding precision@16 = 0.7738 and a "mix" embedding precision@16 = 0.8997; validation was 5-fold CV split by place id (grouped, no leakage), then refit on full data for submission; the team explicitly did **not** use a transformer and still reached top-10 — [Future Architect blog, 7th/1083 solution](https://future-architect.github.io/articles/20220720a/).
- A separate solution repo (53rd/1079) used sklearn + LightGBM + CatBoost + SHAP but its README with numeric details was not retrievable (GitHub markdown README not rendered in fetch) — [oasidorshin/FoursquareLocationMatching](https://github.com/oasidorshin/FoursquareLocationMatching).

### Inferences
- A pure GBDT (LightGBM) pipeline with careful multi-stage candidate reduction, strong string/geo features, and contrastive-learned embeddings can reach near-top-10 performance (maxIoU 0.9935) on this task class **without any transformer**, suggesting transformers are a marginal-gain addition on top of a well-tuned GBDT baseline rather than a prerequisite for a strong score — consistent with the fact that even the very top teams still used LightGBM/XGBoost as one leg of their final ensemble rather than replacing it.
- The universal pattern across top teams is: cheap/coarse blocking → cheap GBDT re-ranking to cut candidates (top-K, e.g. top-40/id) → expensive rich-feature model (GBDT and/or transformer) only on the reduced candidate set → graph/GNN or union-find post-processing to enforce global consistency of match groups. This directly matches our current pipeline shape (block → features → LightGBM → threshold → group), suggesting the highest-leverage next step is adding a second, richer-feature GBDT pass on a smaller top-K candidate set plus explicit graph-consistency post-processing, rather than jumping straight to transformers.
- Validation-by-group (5-fold split by place id) mirrors our own group-split-by-S1-entity rule and is confirmed as the standard practice in the top Foursquare solutions, not just a hackathon-rule artifact.

### Gaps
- Could not confirm 1st/2nd/3rd/4th/5th place teams' exact final IoU scores, exact blocking recall percentages, or precise candidates-per-record counts for the *very top* teams (1st–5th) — Kaggle's writeup and discussion pages are client-rendered and WebFetch only returned page titles, not body text; only the 7th-place team's numbers were independently obtained (via a non-Kaggle blog mirror).
- Could not quantify precisely how much the transformer reranking stage improved IoU over the LightGBM-only stage for the 1st/2nd place teams specifically (search snippets describe the *architecture* but not an ablation delta). Given the 7th-place team matched near-top scores without transformers, the marginal transformer gain in this competition is plausibly small (sub-1% IoU) but this is inference, not a cited number — flagged as unconfirmed.
- Feature-importance ranking ("which LightGBM features mattered most") was not obtained in ready comparable detail across teams; only feature *categories* (string edit-distance, geo distance, embedding similarity/SVD) were confirmed as present, not their relative SHAP/importance ranking.

## Kaggle "Shopee - Price Match Guarantee" (2021) and SIGMOD Programming Contests (2020-2022)

### Takeaway
Shopee winners used multimodal blocking/matching (image embeddings from CNN/ViT backbones + text embeddings, both trained with ArcFace metric-learning loss, plus TF-IDF) combined via per-modality thresholds and a union of matches; text-only techniques (TF-IDF, multilingual BERT) are the directly relevant piece for our name/address-only task. The SIGMOD 2022 blocking contest (entity-resolution, pure blocking task, judged on recall with runtime as tiebreaker) was won by embedding entities with a **contrastively pre-trained transformer**, indexing with **FAISS** for approximate nearest-neighbor search, then **re-ranking with a symbolic (string) similarity metric** — i.e., "embed + ANN + symbolic re-rank" is the SOTA blocking recipe from that literature. The SIGMOD 2021 contest (full entity resolution, not just blocking) was won with a much simpler two-stage rule: clean/normalize key fields, then match records by exact/near-exact key-field identity, scored on average F-measure.

### Cited Findings
- Shopee competition goal: identify identical products from image + text description listings ("Price Match Guarantee"), competition ran Mar–May 10, 2021 — [Kaggle competition page](https://www.kaggle.com/c/shopee-product-matching/overview).
- Common winning-tier technique stack: image embeddings from NFNet / Swin Transformer / EfficientNet-B5; text embeddings from DistilBERT / ALBERT / Multilingual BERT / TF-IDF; **ArcFace loss** (not softmax) used for metric learning on both modalities to sharpen the embedding space for threshold-based matching — [search-surfaced solution summary](https://www.kaggle.com/c/shopee-product-matching/overview) via aggregation of GitHub solution repos ([NaquibAlam/Shopee-...-Kaggle](https://github.com/NaquibAlam/Shopee---Price-Match-Guarantee-Kaggle)).
- Post-processing/ensembling trick: predictions were pruned by cross-checking — text-embedding matches were dropped if the corresponding image embeddings were too dissimilar — then final matches were taken as the union of unique matches across the separate image, TF-IDF, and transformer-text models — [search-surfaced summary](https://github.com/NaquibAlam/Shopee---Price-Match-Guarantee-Kaggle).
- SIGMOD 2022 contest task: build a **blocking system** for entity resolution across two product datasets (Notebook-specs ~1M rows / 1M candidate pairs target; Altosight products ~1M rows / 2M candidate pairs target; 3M total candidate pairs output), evaluated primarily on **recall** (fraction of true matches retained in the candidate set) with runtime as tiebreaker — [transactional.blog SIGMOD contest archive, 2022](https://transactional.blog/sigmod-contest/2022).
- SIGMOD 2022 winner (Team WBSG — Alexander Brinkmann & Ralph Peeters, University of Mannheim, 55 teams total): embedded entity descriptions with a transformer **pre-trained via supervised contrastive learning** (plus extra pre-training on schema.org-annotated CommonCrawl data), indexed embeddings with **FAISS**, did nearest-neighbor search in embedding space, then **re-ranked retrieved pairs with a symbolic (string) similarity metric** — [University of Mannheim news](https://www.uni-mannheim.de/en/news/wbsg-wins-sigmod-programming-contest-2022/).
- SIGMOD 2021 contest task: full entity resolution (not just blocking), submissions ranked by average F-measure across datasets — [transactional.blog SIGMOD contest archive, 2021](https://transactional.blog/sigmod-contest/2021); winning team (Weibao Fu, Peiqi Yin, Lan Lu, Southern University of Science and Technology) used a two-part pipeline: (1) row-by-row data cleaning/reorganization of CSVs down to key field values, (2) entity matching by assigning each record an identifier derived from its cleaned key-field values and resolving records sharing an identifier — [search-surfaced summary of yinpeiqi/SIGMOD-2021-program-contest](https://github.com/yinpeiqi/SIGMOD-2021-program-contest).

### Inferences
- Across both Shopee and SIGMOD-2022, the winning recipe for the retrieval/blocking half of the pipeline is consistently "dense embedding + ANN index + cheap symbolic re-rank," not raw string blocking alone — this is a candidate upgrade path for our blocking stage if 94% recall needs to improve, though it adds embedding-model dependency (must stay MIT/Apache-2.0, ≤8B params per our rules).
- SIGMOD 2021's winning approach (clean key fields → near-exact key matching) shows that for well-structured, less noisy data a much simpler rule-based match can win a contest judged on F-measure; this is a useful "cheap baseline" sanity check but is less applicable to our task since ~26% of our noisy records are near-duplicate distractors specifically designed to defeat simple key-normalization matching.

### Gaps
- Could not find a citable, dedicated "1st place solution" writeup with exact metrics (F1/IoU, candidate counts, threshold values) for Shopee — search results surfaced only aggregated GitHub solution repos and a general technique summary, not a single authoritative top-1 writeup with numbers. The official top solutions likely exist as Kaggle discussion posts but were not surfaced/fetchable in this session.
- No blocking-recall or final-score numbers were obtained for either SIGMOD 2021 or 2022 winners (the archive pages describe task setup and required candidate-set sizes but not the winners' achieved recall/F-measure/runtime).

## Pairwise matchers: GBDT vs Ditto vs AnyMatch vs LLM prompting

### Takeaway
On "dirty" (noisy, near-duplicate-distractor-style) benchmark datasets, fine-tuned transformer matchers (Ditto) beat GBDT/string-similarity matchers (Magellan) by the largest margins specifically on the dirtiest data — e.g., Ditto 85.69 vs Magellan 37.4 F1 on Dirty Walmart-Amazon — which is directly relevant to our ~26% near-duplicate-distractor problem. However, a small fine-tuned LM (AnyMatch, GPT-2-scale) gets within ~4.4 F1 points of GPT-4 prompting (MatchGPT) at ~3,900x lower cost, and both underperform Ditto/task-specific fine-tuning on some individual dirty/structured datasets — the literature does **not** show GBDTs matching transformers on genuinely dirty data; GBDTs are competitive mainly on clean, well-structured data.

### Cited Findings
- Ditto (VLDB 2021) vs Magellan on **Dirty** benchmark datasets (Table 5 of the Ditto paper), exact F1: Dirty DBLP-ACM — Magellan 91.9, DeepMatcher 98.1, Ditto 99.03; Dirty DBLP-Scholar — Magellan 82.5, DeepMatcher 93.8, Ditto 95.75; Dirty iTunes-Amazon — Magellan 46.8, DeepMatcher 79.4, Ditto 95.65; **Dirty Walmart-Amazon — Magellan 37.4, DeepMatcher 53.8, Ditto 85.69** — [Ditto paper, VLDB 2021 (ar5iv mirror)](https://ar5iv.labs.arxiv.org/html/2004.00584).
- Ditto's average performance degradation from clean→dirty versions of the same datasets is only 0.57 F1 points, vs. 8.21 points degradation for DeepMatcher+, i.e. Ditto is far more robust to injected noise (attribute shuffling, missing values) than the classical feature-based approach — [Ditto paper (ar5iv mirror)](https://ar5iv.labs.arxiv.org/html/2004.00584).
- On clean/structured datasets (Cameras, Computers), Ditto still clearly outperforms Magellan: Cameras F1 80.89–93.78 (Ditto) vs 55.63–62.84 (Magellan); Computers F1 80.76–88.62 (Ditto) vs 59.23–64.13 (Magellan); on a large company-matching dataset (789K/412K records) Ditto reaches 96.5% F1 — [search-aggregated Ditto benchmark results, VLDB Journal follow-up](https://link.springer.com/article/10.1007/s00778-023-00779-z).
- AnyMatch (2024, fine-tuned small LM, GPT-2 scale) vs. baselines, mean F1 across 9 benchmark datasets / 13 baselines: **AnyMatch 81.96**, MatchGPT [GPT-4 prompting] 86.36 (highest), Ditto 66.05 (note: lower mean here than the Dirty-only numbers above — different, broader benchmark mix), ZeroER (parameterless) 66.86, StringSim baseline 40.21 — [AnyMatch paper, arXiv 2409.04073](https://arxiv.org/html/2409.04073v1).
- AnyMatch cost/throughput: inference throughput 693,999 tokens/s (on 4×A100 GPUs) vs. Jellyfish (fine-tuned Llama2-13B) 26,721 tokens/s vs. MatchGPT variants 752–2,108 tokens/s; inference cost per 1,000 tokens: MatchGPT[GPT-4] $0.015 vs AnyMatch $0.0000038 (~3,899x cheaper); AnyMatch reaches within 4.4% mean F1 of GPT-4 prompting at that cost — [AnyMatch paper, arXiv 2409.04073](https://arxiv.org/html/2409.04073v1).
- Peeters & Bizer have published work specifically on applying ChatGPT/LLMs to entity/product matching, and a companion benchmark "WDC Products: A Multi-Dimensional Entity Matching Benchmark" (2023) is widely cited in this literature, with a further general LLM-for-entity-matching paper — [arXiv 2310.11244, "Entity Matching using Large Language Models"](https://arxiv.org/pdf/2310.11244) (paper located but its PDF could not be parsed as text by the fetch tool in this session; exact F1 numbers from this specific paper were not extracted).

### Inferences
- The specific case most analogous to our hackathon (near-duplicate distractors: same address, one word changed) is best represented by the "Dirty" Ditto benchmarks, where the GBDT/string-feature baseline (Magellan) loses by the largest margin on the dirtiest, most ambiguous data (37.4 vs 85.69 F1 on Dirty Walmart-Amazon). This suggests our current pure string-feature + LightGBM approach (local F0.5 = 0.9555) is plausibly leaving meaningful accuracy on the table specifically on the ~26% distractor cases, and a transformer-based reranker for the *uncertain* band of pairs (not all pairs) is the highest-leverage architectural change suggested by this literature, not a wholesale replacement of LightGBM.
- AnyMatch's result — a small (GPT-2-scale, well under our 8B parameter cap) fine-tuned LM getting close to GPT-4-prompting performance at a fraction of the cost — supports a design where we fine-tune a small open, permissively-licensed LM/cross-encoder on our own labeled training pairs (allowed under the competition's "pretrained models are OK if MIT/Apache-2.0 and ≤8B params" rule) rather than attempting any hosted-LLM-prompting approach (which is explicitly disallowed by the "no web lookups / no hosted LLM API calls" competition rule).

### Gaps
- Could not extract the specific Peeters & Bizer (2023–2025) F1 numbers comparing zero-shot/few-shot LLM prompting vs. fine-tuned Ditto/RoBERTa baselines — the arXiv PDF (2310.11244) could not be parsed to text by the available fetch tooling in this session (binary PDF stream, FlateDecode compressed). This is a genuine gap; the report-writer should treat the general claim "GPT-4 prompting can rival or exceed fine-tuned matchers in low-resource/zero-shot settings" as directionally supported by the AnyMatch paper's comparison numbers above, but not confirmed from Peeters & Bizer's own paper directly.
- The AnyMatch mean-F1 numbers (66.05 for Ditto, 81.96 for AnyMatch) are from a *different, broader* 9-dataset benchmark mix than the Ditto paper's own Dirty-datasets table, so the two sets of numbers are not directly comparable/consistent with each other — this is flagged rather than merged into one ranking.
- No head-to-head "GBDT vs Ditto vs AnyMatch vs LLM prompting, same datasets, same table" was found in one place; the notes above stitch together numbers from two different papers/benchmarks, which the report-writer should treat as approximate signal, not a rigorous single-source ranking.

## CPU feasibility: small cross-encoder reranking and fine-tuning

### Takeaway
Concrete CPU throughput numbers were only partially obtainable: a bi-encoder (all-MiniLM-L6-v2, not a cross-encoder) is reported at roughly 237 sentences/sec on a standard CPU (~14,200/min) and 800 queries/sec at batch size 64 on a CPU-only c7g.large instance; ONNX+int8 quantization is reported to give ~2-3x further CPU speedup generally, but no single authoritative source gave an exact pairs/sec number for a **cross-encoder** MiniLM under ONNX+int8 on CPU — estimates from secondary/aggregator sources suggested roughly 16-50 pairs/sec per (unspecified) CPU core-equivalent, which should be treated as a rough estimate, not a hard number. Fine-tuning small (sub-60M-parameter) transformers on CPU within a few hours is described as feasible in secondary sources, but no source gave a directly-relevant benchmark (fine-tuning a MiniLM-class cross-encoder specifically, on a 12-core CPU, in ~6 hours).

### Cited Findings
- all-MiniLM-L6-v2 (22.6M params, bi-encoder) CPU throughput: ~14,200 sentences/minute (~237 sentences/sec) on a "standard CPU"; separately, 800 queries/sec at batch size 64 was reported on a CPU-only AWS c7g.large instance — [search-aggregated, sources include AITinkerers project page and Superlinked model page](https://lausanne.aitinkerers.org/technologies/sentence-transformers-all-minilm-l6-v2). Exact CPU model/core count was not specified in the retrievable snippet, so these numbers cannot be directly converted to "per 12-core laptop" throughput with confidence.
- Sentence-Transformers' own official CrossEncoder efficiency documentation confirms ONNX, OpenVINO, and int8/quantization are supported optimization paths, but the fetched page did **not** contain concrete pairs/sec or latency benchmark numbers for CPU — [Sentence Transformers CrossEncoder efficiency docs](https://sbert.net/docs/cross_encoder/usage/efficiency.html) (page fetched directly; benchmark numbers not present in the accessible content).
- Secondary/aggregator sources (not primary benchmarks) suggest: a ~22M-parameter MiniLM-class cross-encoder scores ~100 pairs in 300–500ms on CPU (vs 50–100ms on GPU); int8 dynamic quantization or ONNX Runtime gives ~2-3x CPU speedup; a MiniLM-L6 cross-encoder run via ONNX+int8 on CPU was reported at 20-60ms latency for scoring ~20 pairs — [aggregator/blog sources surfaced by search, e.g. Medium "10 Rerankers Under 150ms"](https://medium.com/@ThinkingLoop/10-rerankers-under-150-ms-splade-colbert-friends-076b1928e618) (not a primary benchmark; treat as approximate).
- Fine-tuning feasibility (secondary sources, not a single authoritative benchmark): compact transformer models have been trained from scratch on CPU to ~80% accuracy in about 30 minutes for small tasks; models under ~60M parameters are generally described as CPU-fine-tunable "within hours"; LoRA/parameter-efficient fine-tuning is suggested as a way to further reduce CPU training cost — [search-aggregated, e.g. "Training Compact Transformers from Scratch in 30 Minutes with PyTorch"](https://medium.com/pytorch/training-compact-transformers-from-scratch-in-30-minutes-with-pytorch-ff5c21668ed5).

### Inferences
- Given ~237-800 sentences/sec single-stream bi-encoder throughput on CPU (order-of-magnitude, unconfirmed core count) and that cross-encoders are meaningfully slower per-pair than bi-encoder embedding lookups (they process pairs jointly, no caching), reranking 1-3M *uncertain* pairs (not all candidate pairs) in 1-2 hours on 12 cores is plausible only if (a) reranking is restricted to a narrow band of borderline-confidence LightGBM scores rather than all candidates, and (b) batching + ONNX int8 + multi-core parallelism (e.g., one process per core) are all used together. This is an inference from partial numbers, not a directly confirmed benchmark — treat the "1-2 hours for 1-3M pairs on 12 cores" target as unverified and worth a small-scale local timing test before committing engineering time to it.
- Fine-tuning a MiniLM-class (22-118M param) cross-encoder on CPU in ~6 hours is plausible in principle per the general "small transformer, hours, CPU" secondary evidence, but no source directly confirmed this for a cross-encoder entity-matching fine-tune at our data scale (candidate_pairs.tsv could be several million rows). Given the ~2-day time budget and that this is unverified, treat CPU fine-tuning as a stretch goal to be timed early (e.g., 10k-pair sample) rather than assumed to work.

### Gaps
- No primary-source (official model card, ONNX Runtime docs, or vendor benchmark) gave an exact CPU pairs/sec figure for a cross-encoder MiniLM under int8 ONNX quantization specifically — all cross-encoder CPU numbers found were from aggregator/blog sources of unstated rigor and unspecified CPU hardware, and should be re-verified with a local benchmark before being used to plan the pipeline's timing budget.
- No source addressed fine-tuning time specifically for entity-matching cross-encoders (as opposed to generic small-transformer classification tasks) on a 12-core CPU with no GPU; this is a genuine gap and should be resolved with a local pilot run (e.g., 1 epoch on a 50k-pair sample, measure wall-clock) rather than assumed from the general literature.

## Licenses and sizes of candidate pretrained models

### Takeaway
All seven candidates (six embedding/encoder models + LightGBM) are permissively licensed (MIT or Apache-2.0) and well under the ≤8B parameter cap; sizes range from 22.6M (all-MiniLM-L6-v2) to 560M (BAAI/bge-m3, the only encoder in the list not natively CPU-trivial at scale but still far below 8B).

### Cited Findings
- **sentence-transformers/all-MiniLM-L6-v2**: license Apache-2.0; 22.6M parameters; 6-layer MiniLM (DistilRoBERTa-like) encoder, 384-dim output. Note: while the model weights are Apache-2.0, its training data includes MS MARCO and GooAQ, some of which reportedly have restrictions inconsistent with unrestricted commercial redistribution of the *model* per a HuggingFace discussion thread — worth flagging but the model card itself states Apache-2.0 — [HuggingFace model card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) and [license discussion thread](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2/discussions/34).
- **sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2**: license Apache-2.0; ~118M parameters; 12-layer MiniLM, 384-dim output, mean pooling, supports 50+ languages — [search-aggregated model card summary](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2).
- **intfloat/multilingual-e5-small**: license MIT; ~117.65M parameters (some sources also describe it as ~118M/12-layer, 384-dim embedding) — [HuggingFace model page](https://huggingface.co/intfloat/multilingual-e5-small).
- **BAAI/bge-m3**: license MIT; ~560-568M parameters (~1.06GB weights); fine-tuned XLM-RoBERTa base with 1024-dim output, 250K vocab, supports 100+ languages and inputs up to 8192 tokens — [HuggingFace model page](https://huggingface.co/BAAI/bge-m3) and [model size discussion](https://huggingface.co/BAAI/bge-m3/discussions/60).
- **xlm-roberta-base**: standard base architecture (not separately re-confirmed license text in this session's search snippet, but XLM-R is well-established as MIT-licensed by Meta/Facebook — flagged as needing a direct model-card re-check before final adoption since the search snippet for this query returned mDeBERTa details more prominently than XLM-R's own license line).
- **microsoft/mdeberta-v3-base**: license MIT; 12 layers, hidden size 768; ~86M backbone parameters + ~190M embedding-layer parameters (250K-token vocab) = ~280M total parameters; trained on the same 2.5T-token CC100 multilingual corpus as XLM-R; reported to outperform XLM-R-base on XNLI — [HuggingFace model card](https://huggingface.co/microsoft/mdeberta-v3-base).
- **LightGBM**: MIT license, copyright Microsoft Corporation and the LightGBM developers; project repository moved from `microsoft/LightGBM` to `lightgbm-org/LightGBM` — [LICENSE file on GitHub](https://github.com/lightgbm-org/LightGBM/blob/master/LICENSE).

### Inferences
- All seven candidates clear the competition's "MIT or Apache-2.0, ≤8B params" bar comfortably, so the choice among them should be driven by task fit (multilingual robustness for French test data, inference speed on CPU, and embedding dimensionality/index size) rather than license risk. Given the French-generalization requirement, the multilingual options (multilingual-e5-small, paraphrase-multilingual-MiniLM-L12-v2, bge-m3, mdeberta-v3-base, xlm-roberta-base) are more directly relevant than the English-only all-MiniLM-L6-v2.
- Among the multilingual options, multilingual-e5-small (MIT, ~118M params) and paraphrase-multilingual-MiniLM-L12-v2 (Apache-2.0, ~118M params) are the best fit for CPU-only, time-constrained fine-tuning/inference given their smaller size relative to bge-m3 (560M) and mdeberta-v3-base (~280M total).

### Gaps
- xlm-roberta-base's license was not independently re-confirmed with a direct model-card fetch in this session (the search query surfaced mDeBERTa details more prominently); before adoption, fetch https://huggingface.co/xlm-roberta-base directly to confirm the exact license field and parameter count (commonly cited elsewhere as ~270M for base, MIT license, but this specific number was not captured from a primary source in this session).
- No inference-speed or CPU-benchmark numbers were gathered per-model for this batch (e.g., relative throughput of e5-small vs paraphrase-MiniLM-L12 vs mdeberta-v3-base on the same CPU) — only the general MiniLM CPU throughput numbers under "CPU feasibility" above are available, and those are for all-MiniLM-L6-v2 specifically, not the multilingual variants.
